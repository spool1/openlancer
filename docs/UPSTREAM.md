# Engine: the Librelancer fork

OpenLancer runs on a fork of [Librelancer](https://codeberg.org/Librelancer/Librelancer). The fork is a git submodule at `external/Librelancer`, on the branch `openlancer`.

## Rules

- The branch `openlancer` starts at the upstream commit in "Base commit" below. Each OpenLancer change to the engine is a normal commit on that branch. OpenLancer code that does not have to be in the engine stays in OpenLancer's own projects.
- Commit in the submodule first. Then commit the new submodule commit in OpenLancer.
- The subject of each fork commit starts with its change number, for example `OL-0012`. This table and the other documents use these numbers. The next free number is `OL-0073`. OL-0067 to OL-0069 are free too (see the note under the table).
- The fork commits are never submitted upstream. Librelancer does not accept AI-written issues or pull requests, and automated tools must not open them.
- The fork is the public repository `https://github.com/spool1/openlancer-engine` (remote `origin` of the submodule). Push each new fork commit there before you commit the submodule pointer in OpenLancer, so that a new clone can get it.
- The remote `upstream` of the submodule is Librelancer on Codeberg, `https://codeberg.org/Librelancer/Librelancer.git`. Librelancer moved there from GitHub on 2026-10-10, and its GitHub repository holds only a notice now.

## Build the submodule

Prerequisites: .NET 10 SDK, Visual Studio 2022 or 2026 with the Desktop C++ workload, and CMake 4.2 or later. CMake 4.2 is necessary because the upstream shader step always selects the newest Visual Studio.

1. In `external/Librelancer`, run `powershell -ExecutionPolicy Bypass -File .\build.ps1 --assemblyversion 0.0.0-ol GenerateVersion BuildNatives ShaderDependencies`.
2. Open PowerShell in the repo root.
3. Run `dotnet build OpenLancer.slnx`.
4. To get the game and the editor, run `dotnet build external\Librelancer\src\lancer\lancer.csproj` and `dotnet build external\Librelancer\src\Editor\LancerEdit\LancerEdit.csproj`.

A commit that changes native code, for example OL-0019 in `src/cimgui_ext`, needs step 1 again. The OpenLancer builds copy `bin/natives/x64` to their output folders, and `start.bat` builds only the managed code.

Since OL-0035, the natives link the static C and C++ runtime through the toolchain file `scripts/msvc-static-crt.cmake`. CMake reads a toolchain file only when it makes a build folder. So before step 1, delete the folder `obj/x64` of a build from before OL-0035 once. Without this step, the natives still need the Visual C++ Redistributable, and the release check e of `tools/release_check.py` refuses them.

Step 1 writes these outputs:

| Output | Content |
|---|---|
| `src/CommonVersion.props` | Generated version file that every upstream project imports |
| `bin/natives/x64/` | Native libraries that OpenLancer projects copy next to their output |
| `bin/builddeps/` | SPIRV-Cross and DXC for the shader compiler |
| `src/LLShaderCompiler/bin/Debug/` | The shader compiler that `Shader.targets` calls |

Step 4 writes `lancer.exe` to `src/lancer/bin/Debug/net10.0/` and `LancerEdit.exe` to `src/Editor/LancerEdit/bin/Debug/net10.0/`. Start the game with a config file: `lancer.exe <path to .lancer.ini>`.

The build output is ignored by the upstream `.gitignore`. After a build, `git -C external/Librelancer status` must show no change.

### Fixed: `BuildAll` failed when the path has a space

The `BuildEngine` and `BuildSdk` targets publish with `UseArtifactsOutput=true`, so the intermediate path is absolute. `Shader.targets` passed it to `LLShaderCompiler` as `--rsp $(IntermediateOutputPath)...` without quotes, and a space in the path split the argument. OL-0026 quotes the argument. A build of `LibreLancer.csproj` with `--artifacts-path` in a folder with a space compiles all 31 shaders.

## Merge upstream changes

Merge, do not rebase. A rebase changes the commit IDs that the OpenLancer history and the table above refer to.

1. Read the upstream commits since the base commit.
2. In `external/Librelancer`, run `git fetch upstream` and `git merge <upstream sha>`.
3. If a conflict shows that upstream fixed a problem that a fork commit also fixes, keep the upstream fix. Write in the table that the commit is replaced.
4. Run `git submodule update --init --recursive` in `external/Librelancer`.
5. Build the submodule again.
6. Run `dotnet test OpenLancer.slnx`.
7. If a test fails, fix OpenLancer or the fork, or return to the commit before the merge.
8. Update "Base commit" above to the merged upstream commit. `python tools/content_scan.py --fork` checks only the fork changes after this commit. Without this step, the scan also checks the upstream changes of the merge.
